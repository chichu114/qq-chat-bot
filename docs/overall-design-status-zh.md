# QQ 智能体总体设计与完成状态

状态基准：2026-10-11

这份文档描述项目的最终方向、当前代码已经具备的能力，以及还没有完成的部分。状态以
仓库中的实现、配置和自动化测试为依据，不代表某台电脑上的外部账号、模型或服务一定
正在运行。代码完成不等于当前机器已经启用；标为默认关闭的模块仍需单独配置和验收。

## 一、总体目标

项目目标不是重新实现 QQ 协议，也不是修改 NapCatQQ 或 OneBot，而是在两者之上建立一个
可恢复、可审计、可扩展的个人 QQ 智能体：

- NapCatQQ 负责登录 QQ、维持会话并完成 QQ 协议适配；
- OneBot v11 负责把 QQ 事件和发送动作标准化；
- 本项目负责身份与白名单、消息分流、OpenClaw/Ollama 调用、记忆与待办、可靠投递、
  群聊风格、管理面板和故障恢复；
- SQLite、文件导出、Keychain 和本地配置共同承担状态、审计和密钥边界；
- 离线数据集与 CUDA 训练链路独立于在线 QQ 服务，不允许训练过程改变线上配置或发消息。

## 二、总体架构

```text
QQ 用户/群聊
    |
    v
NapCatQQ：QQ 登录、会话、协议适配
    |
    v
OneBot v11 WebSocket：事件输入 / 动作输出
    |
    v
Bridge Runtime
    +-- 入站解析、白名单、限流、去重
    +-- 私聊路由 ------------------------> OpenClaw Agent
    +-- 群聊路由 ------------------------> Ollama / KanagawaWave
    +-- 本地命令 ------------------------> 记忆、待办、提醒、审批
    +-- 媒体与长任务（默认关闭） --------> 独立媒体 API / Task Runtime
    |
    v
SQLite + 可靠发件箱 -> OneBot v11 -> NapCatQQ -> QQ

旁路服务：
    Style Learner  -> 授权来源 -> 抽象风格画像 -> 按群绑定
    Dashboard      -> 本机查询、配置、审批和运维
    Watchdog       -> Bridge / OneBot / NapCat 健康检查与受限恢复
    Offline Trainer-> 审核数据集 -> QLoRA -> 合并模型 -> Ollama
```

代码采用分层边界：

- `domain/`：记忆、待办、调度、动作和群风格规则，不依赖 WebSocket 或 SQLite；
- `application/`：命令链、消息协调、群聊响应、可靠投递、媒体和后台任务；
- `persistence/`：SQLite schema、Repository、Outbox、审批、记忆、路由和审计状态；
- `orchestration/`：规划、执行、验收、预算和追踪接口，目前生产链路仍以单 Agent 为主；
- `runtime/`：OneBot、Ollama、OpenClaw、来源适配器、配置、日志和服务装配；
- 独立进程：Dashboard、Style Learner、Watchdog。

## 三、状态图例

- ✅ 已完成：代码和自动化测试已经存在，可进入部署验收。
- 🟡 已实现但默认关闭：代码已经存在，但默认配置不启用，需要外部服务、账号或人工验收。

### F2 及后续智能编排

### 通用 CUDA 训练器

应独立设计数据模板、LoRA 目标层、显存配置、合并与 Ollama 转换验证。

### 完整跨平台部署

🟠 部分完成。核心 Python 服务可以在通用环境运行，但双击应用、LaunchAgent、Keychain、

安装器和端到端验收尚未统一。

## 六、数据与安全边界

- QQ、网页、Reddit、贴吧、附件和引用内容均按不可信输入处理；
- 私聊和群聊分别执行白名单、触发条件、长度、类型与频率限制；
- 群风格只使用得到授权的来源，并支持撤权后的画像失效/重建；
- OAuth bearer、API Key 和备份主密钥不得进入仓库、日志或 QQ 回复；
- 来源正文不会作为长期知识库注入群聊，群消息也不进入长期群聊记忆；
- 模型不能绕过本地命令链、审批仓库、媒体预算或工具 deny；
- 数据集、SQLite、日志、模型、adapter、GGUF/Safetensors 和本机 `.env` 不进入公开仓库。

## 七、建议后续顺序

1. 稳定现有 NapCat/OneBot、私聊、Outbox、Watchdog 和群聊风格路径，补齐真实运行验收记录。
2. 保持 E4-A 和 F1 默认关闭，分别完成小范围部署、观察期和回滚演练。
3. 对 F1 收集至少一个完整验收窗口的标注、准确率、延迟和成本证据，再决定是否进入 F2。
4. 在任何多 Agent 或外部业务连接器之前，先完成能力档案、预算账本和权限模型。
5. E4-B 按单一连接器逐个交付，不一次性开放邮件、日历和项目管理写权限。
6. E4-C 与双模型议会、DAG、审计模型分别设计和验收，不能用一个总开关同时上线。

## 八、项目“完全完成”的判定

这个项目目前属于“核心单 Agent 与社区风格能力可用，高级编排仍在建设”。要称为整体完成，
至少还需要：

- 现有默认路径在真实 QQ/NapCat 环境完成持续稳定性与恢复演练；
- 默认关闭模块分别通过启用、回滚、成本和隐私验收；
- 明确决定 E4-B、E4-C、F2 以后阶段是实现、延期还是取消；
- 为保留的后续能力补齐代码、测试、运维手册和部署证据；
- 公开发布再次确认不包含账号、群号、凭据、数据集、数据库、日志或模型权重。

在这些条件完成前，README 和发布说明必须继续区分“代码已实现”“默认关闭”“部分完成”
与“尚未实现”，不能用一个总百分比掩盖部署和外部依赖差异。
